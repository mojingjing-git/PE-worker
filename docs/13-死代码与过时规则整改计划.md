### Task A1：修 `jobexec.go` 的 stderr 句柄关闭顺序

**这是全计划唯一的真实运行时 bug。**

**根因：** `src/win/jobexec.go:270-275` 注释写"关掉两个**写端**"，实际关的是 `soWr`（stdout 写端 ✅）
和 `seRd`（stderr **读端** ❌）。导致三件事同时坏：
- `jc.stderrRd` 恒为 0 → `TakeStderrPipe()` 永返 nil → `exec.go:106` 的 `io.Copy(cw, nil)` 立即返回
  `os.ErrInvalid` → **exec 的 stderr 输出全丢**
- `seWr`（stderr 写端）在父进程从未关闭 → 每次 exec 泄漏一个可继承句柄
- 父进程握着写端 → 子进程 stderr 写满 64KB 管道后永久阻塞 → `exec.go:121` 的 `jc.Wait()` 阻塞。
  **不是永久挂死**：`exec.go:112-119` 的 kill watcher 会在 `execTimeoutSec`（60s）到期时
  `jc.Kill()` → `TerminateJobObject`，所以最坏是"任何 stderr 超过 64KB 的命令每次都硬吃满
  60s，然后报一个**误导性的 timeout**"。真实症状是三条：
  ① stderr 恒空 ② 每次 exec 泄一个可继承句柄 ③ >64KB stderr 的命令每次假超时。

**测试为什么没抓到：** `win/jobexec_test.go:33`、`:181` 都写成 `se, _ := io.ReadAll(...)`，
**error 被丢弃**，拿到 nil 就返回空串，断言照样过。

**Files:**
- Modify: `src/win/jobexec.go:270-283`（修关闭顺序）、`:89-92`（删死字段）、`:585-614`（`Take*Pipe` 注释）
- Test: `src/win/jobexec_test.go:25-40`（改为断言 stderr 真有内容）

**Interfaces:**
- Consumes: 无（可独立执行）
- Produces: `JobCmd.stderrRd` 恒为有效句柄；`TakeStderrPipe() *os.File` 在 `h==0` 时才返 nil

// 扫描本包非测试文件里所有「名字 = 字面量」形式的常量。
func scanWin32Consts(t *testing.T) map[string]string {
	t.Helper()
	ents, err := os.ReadDir(".")
	if err != nil {
		t.Fatalf("ReadDir: %v", err)
	}
	out := map[string]string{}
	fset := token.NewFileSet()
	for _, e := range ents {
		name := e.Name()
		if e.IsDir() || !strings.HasSuffix(name, ".go") || strings.HasSuffix(name, "_test.go") {
			continue
		}
		f, err := parser.ParseFile(fset, filepath.Join(".", name), nil, 0)
		if err != nil {
			t.Fatalf("ParseFile %s: %v", name, err)
		}
		for _, d := range f.Decls {
			gd, ok := d.(*ast.GenDecl)
			if !ok || gd.Tok != token.CONST {
				continue
			}
			for _, s := range gd.Specs {
				vs := s.(*ast.ValueSpec)
				for i, n := range vs.Names {
					if i >= len(vs.Values) {
						continue
					}
					bl, ok := vs.Values[i].(*ast.BasicLit)
					if !ok {
						continue // 非字面量（组合表达式）不纳入机械比对
					}
					out[n.Name] = name + ":" + bl.Value
				}
			}
		}
	}
	return out
}
