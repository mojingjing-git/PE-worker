# 视觉与截图支持设计

> 用户需求：加一个视觉模型支持，API 侧声明支持视觉之后，让 LLM 能截图、能读图片。工具数从 13 增到 **14**（功能工具）。
> 本文是这一块的设计依据 —— 它比"多一个工具"复杂，牵扯到编码、API 协议差异、token 预算和 GUI 显示。

---

## 1. 加视觉之后，`screenshot` 从"可选"变成"核心"

之前 `docs/02` 把 `screen`（截屏）放在 Tier 3，理由是「有 ToDesk，截屏意义不大」。**那个判断的前提是没有视觉模型。**

有了视觉之后完全变了 —— LLM 能**亲眼看见**：

- 蓝屏的具体错误码和上下文（`0x0000007B` 配的是哪个驱动）
- 错误对话框上到底写了什么
- 分区工具的界面状态（哪些分区、什么文件系统、有没有未分配空间）
- 安装程序卡在哪一步
- ToDesk 没连上时，PE 桌面到底是什么样

**这正是 `PE_SmartFixer` 的核心卖点** —— 它用 Qwen-VL 看图诊断蓝屏，作者把它当作第一卖点来宣传。我们要做同类功能，视觉是绕不过去的。

**所以：`screenshot` 是 MVP 核心工具，不是可选项。**

---

## 2. 工具设计：14 个

只新增 **1 个**工具，保持 Pi 式的极简：

| # | 工具 | 说明 |
|---|---|---|
| 1 | `exec` | 执行命令 |
| 2 | `run_script` | 多行批处理 |
| 3 | `read` | 读文件 —— **扩展：遇到图片扩展名时返回图片内容块** |
| 4 | `write` | 写文件 |
| 5 | `edit` | 精确搜索替换 |
| 6 | `ls` | 列目录 |
| 7 | `find` | 递归找文件 |
| 8 | `sysinfo` | 系统信息 |
| 9 | `diskinfo` | 磁盘与卷 |
| 10 | `netinfo` | 网络 |
| 11 | `ps` / `kill` | 进程列表与结束 |
| 12 | `download` | 拉文件 |
| 13 | `hash` | 文件校验 |
| 14 | **`screenshot`** | **截屏 → 让模型看图** |

**为什么不给"读图片"单独开一个工具？** 因为 `read` 本来就在读文件，图片只是另一种文件类型。多开一个工具会让模型在"该用 read 还是 view_image"上犹豫，也白白多占系统提示词的 token。**Pi 的哲学就是四个工具能办的事不要拆成八个。**

### `screenshot` 的参数

```
screenshot(path, region?, scale?, delay_ms?)
```

| 参数 | 说明 |
|---|---|
| `path` | 存到哪（**必须落盘**，见第 7 节） |
| `region` | 可选：`full`（默认）/ `window:<标题关键字>` / `rect:x,y,w,h` |
| `scale` | 缩放后长边像素，默认 1280，上限 1568 |
| `delay_ms` | 延迟抓取（等菜单弹出来）。默认 0 |

## 3. ⚠️ 一个必须先搞清楚的协议差异：图片能不能放在 tool_result 里

这是最容易踩坑的地方 —— **两家 API 对"工具返回值里能不能带图"的处理不一样**：

| 提供方 | tool 结果能否直接带图 | 做法 |
|---|---|---|
| **Anthropic** | ✅ **可以** —— `tool_result` 的 content 支持 `image` block | 直接把 image block 放进去 |
| **OpenAI 兼容**（DeepSeek / Qwen / Ollama / 大多数国产 API） | ❌ **不行** —— `role:"tool"` 的消息只能是字符串 | 图片必须作为**紧跟在 tool 结果之后的 user 消息**插入 |

### 建议的统一做法

**放弃"放进 tool_result"，统一走「工具返回一句文本 + 紧随其后插一条 user 消息带图」。**

理由：
1. 两种 API 都能用，一套代码不用分叉
2. Anthropic 也接受这种写法，不会出错
3. 模型对"用户发来一张图"的理解反而更自然

工具返回值长这样：

```json
{"ok":true,"data":{"path":"X:\\tmp\\shot1.png","width":1280,"height":720,"bytes":287441,"note":"见随后的图片消息"}}
```

紧接着追加：

```json
{"role":"user","content":[
  {"type":"text","text":"[screenshot 结果] X:\\tmp\\shot1.png"},
  {"type":"image_url","image_url":{"url":"data:image/png;base64,...."}}
]}
```

## 4. PE 里怎么抓屏、怎么编码

### 抓屏本身很简单

`GetDC(NULL)` → `CreateCompatibleDC` / `CreateCompatibleBitmap` → `BitBlt` → 存位图。
全是 XP 就有的基础 GDI API，`user32` + `gdi32` 就够，**没有任何版本兼容风险**。

### 编码是真正的分岔点

| 方案 | 成本 | 评估 |
|---|---|---|
| **裸写 BMP** | 约 40 行 | ❌ **不能用** —— 1920×1080 约 8MB，base64 后约 11MB，超过所有 API 的图片上限 |
| **GDI+**（`gdiplus.dll`） | 约 20 行 | ⚠️ 依赖 `gdiplus.dll`，精简 PE / 老 XP PE **不保证有**；还要走 `GdiplusStartup` 那套 |
| **`stb_image_write.h`**（C） | 引入单头文件 | ✅ 公有领域、零 DLL 依赖、直接编进 exe |
| **`image/png`（Go 标准库）** | 0 行 | ✅✅ **白送**，还附赠 `image/jpeg`、`image/draw`（缩放） |
| **`std.compress.flate`（Zig）** | 约 100 行 | ✅ 自己拼 PNG 头，无外部依赖 |

**结论：**
- **选 Go**：截图 → 缩放 → PNG 编码 ≈ 30 行，全在标准库。**Go 又赢一次。**
- **选 C**：把 `stb_image_write.h` 加进来（单文件，编进 exe）。
- **选 Zig**：用 `std.compress.flate` 自己写 PNG（格式很简单），或者也链 stb。

### 缩放

C 用 `StretchBlt`（会做最近邻，界面截图够用）；Go 用 `image/draw` 的缩放。

**必须缩放**，原因见下一节。

## 5. token 与体积预算（这块比工具本身重要）

**一张图进上下文大约 1000～1500 token**（取决于分辨率）。这个成本远高于任何文本工具结果。

### 四条硬规则

1. **长边 ≤ 1280px。** Anthropic 上限 1568px、OpenAI 上限 2048px —— 取最保守的 1280，兼容所有家。
2. **界面截图用 PNG**（无损，文字边缘清晰）；**如果将来要拍照片类内容，用 JPEG q=80**。
3. **单张 base64 ≤ 约 1MB。** 超了就再降一档分辨率重编。
4. **历史裁剪 —— 这条最关键：**
   > 只保留**最近 2 轮**里的图片，更早的图片从历史里替换成一行文本 `[截图已省略 X:\tmp\shot1.png]`。
   >
   > 不裁剪的话，连着看四五张图，上下文直接爆掉，而且每一轮都在为这些旧图重新付费。

### 一次调用最多返回 1 张图

允许"一次截 5 张"看起来很灵活，实际会让模型一口气把上下文吃满。要多个视角就多调几次。

## 6. 配置与能力声明

```ini
[llm]
; 1 = 模型支持视觉，把 screenshot 工具发给模型
; 0 = 不支持，摘掉 screenshot，read 遇到图片只返回文字描述
vision = 1
```

### 为什么要在配置里声明，而不是自动探测

不靠谱。同名模型的不同版本视觉支持情况不一样，各家命名也不统一（有的叫 `-vl`、有的靠模态参数、有的只是同一名字的新版本偷偷支持了）。**探测错了的代价是模型调用一个它看不懂结果的工具，白烧 token。**

### `vision = 0` 时的行为（必须处理好）

1. **把 `screenshot` 从工具列表里摘掉** —— 别让模型看见它
2. `read` 遇到 `.png` / `.jpg` / `.bmp` 时，只返回 `{"type":"image","bytes":287441,"note":"当前模型不支持视觉，无法查看"}`

## 7. GUI 怎么显示截图

现在的日志区是纯文本 EDIT，**显示不了图**。三个选择：

| 方案 | 成本 | 建议 |
|---|---|---|
| **只在日志里打印路径** | ★ | **V1 就这个**：`  -> screenshot  已存 X:\tmp\shot1.png`，人自己在 ToDesk 里打开看 |
| 单独一个图片预览窗口 | ★★ | V2：一个 `WS_POPUP` 窗口 + `SS_BITMAP` 的 STATIC，用 `LoadImage` 直接读 BMP；**PNG 要先解码成 BMP 才能给 STATIC** |
| 在日志区里嵌图 | ★★★★ | 别做 —— 等于自己重写一个富文本控件，跟当初"不用 comctl32"的决策直接冲突 |

> **关键结论：截图一定要落盘。** 不只为了发给模型，更是为了人能在 ToDesk 窗口里直接打开看 —— 这是 PE 场景下人和 agent 共享同一份"现场记录"的方式。

---

## 8. 什么场景值得截图

**值得：** 蓝屏画面 / 错误对话框 / 安装程序卡住的界面 / 分区工具界面 / 桌面整体状态

**不值得：** 纯文件操作、命令行输出 —— 这些用 `exec` 拿文本**又准又省 token**

> **提示词里必须写清楚：能用文本拿到的信息不要截图。** 否则模型会滥用视觉，每次都截一张"确认一下"，token 成本直接翻十倍。

---

## 9. 与 Tier 3 的联动

单独用 `screenshot` 经常"不知道该截什么"。配一个**窗口枚举工具**（`win`：列出窗口标题 + 坐标 + 是否可见）会让截图精准得多 —— 模型可以先列窗口，再按标题截。

但**先不做**。等 V1 跑通、真的遇到"截不准"的问题再加。

---

## 10. 对 MVP 的净影响

| 项 | 变化 |
|---|---|
| 功能工具 | 13 → **14**（新增 `screenshot`） |
| 辅助工具 | `selftest`、`help` 不变 |
| `read` | 增加"图片扩展名 → 返回图片内容块"的分支 |
| 配置 | 新增 `[llm] vision` 开关 |
| GUI | V1 只打印截图路径；V2 加预览窗口 |
| 历史管理 | **必须实现图片裁剪**（只留最近 2 轮） |
| 语言选型影响 | **Go 的优势进一步扩大** —— `image/png` + `image/draw` 全在标准库，C 要额外引入 stb |
