## 准备

1. 把 `dist/spike386/` 整个文件夹拷到 U 盘（5 个 exe，共约 13MB）
2. 进 PE，打开 cmd
3. `cd` 到那个文件夹
4. **确认 PE 里有没有网**（`ipconfig` 看一下有没有拿到 IP）

> 如果 PE 里没有 `cd` 到 U 盘的盘符，先 `diskpart` → `list volume` 找一下。

## ① 先跑这个 —— `hello.exe`

```cmd
hello.exe
```

**这是总开关。** 如果它都跑不起来，后面不用试了。

- ✅ 打印出一堆系统信息和 `RESULT: hello completed without crashing.` → 记下来
- ❌ 弹"不是有效的 Win32 应用程序" → 架构不对，换 `spike64` 试试
- ❌ 弹缺 DLL（`找不到 xxx.dll`）→ **把这个 DLL 名字记下来，这是最有价值的反馈**
- ❌ 闪一下就没了 → 在 cmd 里跑（上面就是这么写的），别双击

顺手也把内存测了：

```cmd
hello.exe -alloc 256
```

记下 `-- allocation test` 那几行的 `phys avail` 和 `virt avail`。

## ② `dlls.exe` —— 这个最重要

```cmd
dlls.exe
```

它会跑遍各种代码路径（建窗口、GDI、进程枚举、网卡、DNS、TLS、HTTPS GET），然后列出**运行期实际加载的所有模块**。

**关键改动（2026-09-11）**：原来只能靠"跑代码路径"触发加载，而**离线 PE 上走网络的路径会失败，`ws2_32`/`crypt32`/`dnsapi` 就不会被载入，清单直接漏报它们** —— 你会据此以为 PE 里不需要这几个 DLL。现在 spike 会先**显式加载一份"声明的依赖集"**（不依赖网络），所以清单在任何情况下都完整。

所以现在要看两段，**第一段才是决定性的**：

```
-- DECLARED DEPENDENCY CHECK -- (must all be present)
  OK       kernel32.dll
  ...
  ABSENT   xxx.dll  <-- declare it in the PE or the build is wrong
  declared=11 absent=0
```

**把这两段都贴回来：① `DECLARED DEPENDENCY CHECK` 段（有 `ABSENT` 行就是硬结论）② `SYSTEM DLL CHECKLIST` 段。**

（顺便说明：`ABSENT` 是**直接结论**，不再需要你人肉比对 `X:\Windows\System32`。如果你想再核一遍也可以，那就是下面这段：）

然后麻烦你顺手做个对照 —— 这是本次测试的核心目的：

```cmd
dir X:\Windows\System32\*.dll /b >X:\dlls_in_pe.txt
```

（或者直接 `dir X:\Windows\System32\ | findstr /i "crypt32 psapi gdi32 ws2_32 mswsock iphlpapi bcrypt advapi32 ntdll"`）

**重点确认这几个在后面那份清单里的存在情况：**

| DLL | 干什么用 | 不在会怎样 |
|---|---|---|
| `crypt32.dll` | 证书链校验（CryptoAPI） | TLS 可能整个走不通 |
| `psapi.dll` | 进程枚举 | `ps` / `kill` 工具受影响 |
| `gdi32.dll` | 截图 | `screenshot` 受影响 |
| `ws2_32.dll` | 所有网络 | 网络全废 |
| `mswsock.dll` | Go net 的扩展 socket | 网络可能起不来 |
| `iphlpapi.dll` | 网卡信息 | `netinfo` 受影响 |
| `bcrypt.dll` | 随机数/加密 | TLS 可能受影响 |

## ③ `gui.exe` —— 看窗口

```cmd
gui.exe -secs 10
```

应该弹出一个窗口，里面有：
- 一大块日志区（只读、可滚动、可选中复制）
- 一个输入框 + 两个按钮（发送 / 停止）
- 底部一行状态栏

同时 10 秒后自动关闭。**注意观察这几件事，都是 PE 里特有的风险：**

- [ ] 窗口**会不会显示**出来
- [ ] 窗口标题栏文字**是不是乱码**
- [ ] 日志区的**文字能不能看清**（字号、字体有没有问题）
- [ ] **中文会不会乱码**（日志里我写的是英文，本来就不会乱）
- [ ] 窗口在 PE 的分辨率下**有没有超出屏幕**
- [ ] 定时器有没有在跑（日志区会每秒多一行 `tick N`）

如果窗口出来但位置/大小不对，告诉我 PE 的分辨率。

## ④ `https.exe` —— 网络与证书

```cmd
https.exe
```

**前置条件：PE 里得能上网。** 默认打 `https://letsencrypt.org/`。

> 为什么默认不是 `example.com`：那个站点的证书链根 CA 太老，**旧系统的根库里也有**，于是 `tls-system` 必然成功 —— 这个实验就**无法证伪**"PE 根库缺新 CA"这个假设，只会给出虚假安心。`letsencrypt.org` 的链末端是 **ISRG Root X1**（2015 年的根），正是老 PE 最可能缺的那一类。

贴回 `SUMMARY` 那五行的结果。**唯一的门禁是这一行：**

```
tls-bundle     ← 用我捆绑的 CA bundle（生产路径，必须 OK）
```

**预期**：`tls-bundle` 必须 OK，否则生产路径就是坏的。

`tls-system` 那行**只是参考**，而且要注意：

- `tls-system` FAIL 而 `tls-bundle` OK → **正好验证了我们的判断**，捆绑 CA bundle 是必需的
- 两个都 OK → **这不能说明 PE 的根库没问题**，只说明"这一个站点的根 CA 恰好在这个 PE 里存在"。真正要紧的是 `tls-bundle` 通过

如果 `tcp` 那行就 FAIL 了，那是网络问题（PE 里没配好网），不是证书问题。如果 `tls-insecure` 也 FAIL，那是 Go 运行时/DLL 问题，不是证书问题。

## ⑤ `job.exe` —— 中止机制（**Win7 PE 上最关键的一项**）

```cmd
job.exe -hold 15
```

这个会起一个 `cmd.exe → ping.exe` 两层进程树，然后用两种方式尝试杀掉它。**关键看这两行：**

```
[1] IsProcessInJob(...)  -> inJob=?
[4] AssignProcessToJobObject  -> OK / FAIL
```

**这三种结果的含义：**

| 结果 | 含义 | 后续动作 |
|---|---|---|
| `inJob=0` 且 `[4] OK` | 完美，走 job 路径 | 主方案用 job |
| `inJob=1` 且 `[4] OK` | PE 支持嵌套 job（可能是 Win8+ 内核的 PE） | 主方案用 job |
| `inJob=1` 且 `[4] **FAIL**` | **Win7 的限制，我们预测的情况** | **主方案必须走自实现杀树**（已经写好了，就在这个 spike 里） |

**这三种情况都能接受** —— 因为自实现杀树我已经写好了，而且本机验证过能用。第 `[7]` 步就是在独立测它：

```
[7] self-contained tree kill on a fresh tree
    killed 3, errors 0
    still alive: 0  -> OK
```

**只要 `[7]` 是 OK，中止机制就没问题**，不管 job 那条路通不通。

顺手也看一下：

```cmd
job.exe -diag
```

把输出贴回来（这是结构体尺寸的诊断，用来确认 386 对齐修复在真 PE 上也对）。
