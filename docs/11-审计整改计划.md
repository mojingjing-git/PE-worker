### 8.2 【最重要】`IsProcessInJob`：结论反转了三次

这条是本轮**最值得留档**的教训 —— 审计报告本身也会错，而且错了两次。

| 轮次 | 说法 | 结局 |
|---|---|---|
| 初版审计 | 传 NULL Job 会触发快路径崩溃，改用 `NtQueryInformationProcess` 绕过 | **被证伪**：新实现实测 0/20 成功，确定性永远返回错误 |
| 第二轮复审 | 真凶是 `GetCurrentProcess()` 的 pseudo-handle，API 不接受它 | **被证伪**：`OpenProcess` 拿的全权限真句柄照样崩 |
| 第三轮实测 | 两条都不是。真规律是：只要 hJob 通过句柄校验（NULL 或真 job 都算）就崩；hJob 是能被立刻判定无效的假句柄时反而干净返回 | **实测确认**（9 场景 × 双架构） |

最终修法：**诚实降级，恒返 `(false, nil)`**。

试过但**不能用**的两条替代路径（都已实测排除）：
- `NtQueryInformationProcess(class=3)`：确定性失败，且 class 3 不在官方 SDK 的 `PROCESSINFOCLASS` 枚举里
- `ntdll!NtIsProcessInJob`：**不崩**，但实测它**区分不出归属** —— `AssignProcessToJobObject` 把进程成功塞进 job 之后（ret=1），它仍返回 `inJob=false`。拿它当判据会**静默误判**

> **为什么"崩"反而好过"静默误判"**：一个会崩的函数至少有迹可循（exit code + 无日志）；一个静默给出错误归属的函数，会让 Win7 无嵌套 job 的坑复发而无人察觉 —— 正好撞上本项目最忌讳的失效模式。

配套：`job_test.go` 那两个零断言测试（一个 `t.Skip` 一个只 `t.Logf`，还把"会崩"误注为"需要 admin"）改成真断言，并加了防回归 —— 若 `inJob` 变成 `true` 直接 fail，防止有人把探测悄悄接回来。

### 8.3 worker 实测推翻了任务给的方案

**S5**：任务要求"用 argv 直传替代拼 cmd 字符串"。worker 写探针后发现 **argv 直传照样能被注入** —— `exec.Command` 在 Windows 走 `syscall.EscapeArg`，把 `"` 编成 `\"`，而 **cmd.exe 不认这个转义**，引号一闭合后面的 `&` 重新变成分隔符。

于是改成**完全不经过 cmd.exe** 的纯 Go 实现（`os.ReadDir` / `os.ReadFile` / `filepath.WalkDir`）：零注入面不是"看起来堵住了"，是**没有解析器可注入**。顺带修好含空格路径（原先 100% 失败）与 `find` 通配符（原先静默返回 0 行）。

**S4**：worker 自己踩到并修了一个 Windows 专属 bug —— `errors.Is(err, syscall.ECONNREFUSED)` 在 Windows 上**恒为 false**（WSA errno 不翻译成 syscall 的"发明值"），导致"连接被拒不重试"在 386 主战场上完全失效（实测 9.01s 仍在重试）。改判 `net.OpError.Op == "dial"` 后降到 0.0Xs。
