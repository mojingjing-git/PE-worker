## 一、T0 · 线程安全：`wstrKeep` 加锁

> ✅ **已完成** —— commit `637d0f8`（+ 复审整改 `338ae9a`）。实施记录见 §十。

### 问题

`win/wstr.go` 的 `wstrKeep` / `wstrKeepSlices` 是**无锁包级全局 slice**，
而调用方横跨两个线程：

```
T1 = UI 线程    main.go:188 OnStop 打 `!! user abort`；main.go:184 OnSend 队列满打 warn
T2 = worker    loop.go 内 5 处 logx.Info/Error
```

`logx.logf` 对**每条**日志行调 `win.Ptr()` → 两条并发 `append` 竞态。

### 危害

丢一次 append 不是"少一行日志"：那个 `*uint16` 从此**只被 `uintptr` 引用** →
GC 立刻可回收 → UI 线程 `appendLog`（`gui.go` `(*uint16)(unsafe.Pointer(lparam))`）
解引用野指针 → 随机花屏/崩溃。`logx.go` 里的 `win.KeepAlive(lp)` **救不了**
—— KeepAlive 只保证本语句之前存活，而这里的解引用跨越线程边界。

### 丢失率实测（审阅 agent，386 多核，5 轮取区间）

| 并发 | 理论 | 实测保留 | **丢失率** |
|---|---|---|---|
| 2 × 200,000 | 400,000 | 262,211 – 281,342 | **29.7% – 34.4%** |
| 4 × 200,000 | 800,000 | 285,997 – 323,827 | **59.5% – 64.3%** |
| 8 × 200,000 | 1,600,000 | 334,409 – 484,808 | **69.7% – 79.1%** |

> ⚠️ **v1 计划写"9.1%"是错的**（那次可能用了 `GOMAXPROCS=1` 或串行对照）。
> 真实场景只有 2 个调用线程，丢失率约 30% —— **非常容易复现，修复效果看得见**，
> 不存在"概率低到测不出"的问题。

### 死锁评估：无风险（已核实）

- `Ptr` / `Hold` / `FromCmdline` 内部只有 `UTF16PtrFromString` + `append`，
  不调用任何其它加锁函数
- `logx` 自己的 `mu` 是"取完就放"（`log.go` Lock → Unlock，之后才调 `win.Ptr`），
  两把锁**不存在嵌套** → 无锁序环路

### 改法

**T0-1**：`Ptr` / `Hold` / **`FromCmdline`** 三处 append 全部加同一把 `sync.Mutex`。

> ⚠️ v1 只写了 `Ptr`/`Hold`，漏了 `FromCmdline`（同样无锁，今天是死代码，
> T2-1 会第一次在生产路径调它）。另外 `Hold` 今天**没有生产调用方**，
> 锁的重点选反了一半。

**T0-2（原"治本方案"）：不做。** 改"所有权交接队列"要动 `logx` + `gui` 数据流，
而 `logx.logf` 的 `lp` 生命周期实际只跨一条 `PostMessage`；PE 会话短、每条日志
约 100 字节，"内存单调增长"在 PE 上不构成实际风险。**收益低于风险。**

### 测试

```go
before := len(wstrKeep)          // ⚠️ 必须断言增量，不能断言 == M
// N goroutine 并发调 Ptr/Hold 共 M 次
// 断言 len(wstrKeep)-before == M
```

> ⚠️ `wstrKeep` 是包级全局，同包其它测试（`TestWstrKeepGrows` 已塞了 500 条）
> 已抬高 baseline，写 `== M` 首次运行必红。
>
> ⚠️ 项目禁 `-race`（`CGO_ENABLED=0` 不可用），此测试是**结构断言**不是竞态检测，
> 注释里要写明，避免后人误以为它能测竞态。

## 二、T1 · 可诊断性：MessageBoxW + 错误出口收口

> ✅ **已完成** —— commit `c5d82da`。实施记录见 §十。

### 问题

PE 里出任何问题，用户拿到的信息是**零**：

1. 产物是 `-H windowsgui`（**没有控制台**），`os.Stderr` 全部丢弃
2. `--console` 是**空实现**（`main.go` 只有 `_ = *consoleFlag`），却承诺弹控制台
3. 三级日志路径都可能失败：`exeDir/smith.log`（U 盘常只读）→ `X:\tmp\` → `C:\tmp\`
4. 全败时只 `fmt.Fprintf(os.Stderr, ...)` 然后 `return 1` —— 丢弃

**PE 现场：双击 smith.exe，闪一下就没了。**

### 改法

**T1-1 · `win/msgbox.go`（新增，~30 行）—— 用 W 版不用 A 版**

> ⚠️ **v1 写的是 `MessageBoxA`，会把中文显示成乱码。**
> `MessageBoxA` 按系统 ANSI 代码页解释字节，Go 的 string 是 UTF-8。
> 审阅 agent 实测本机 `kernel32!GetACP() = 936`（简体中文 GBK）——
> UTF-8 中文按 GBK 解释必然乱码，**直接废掉 T1 的立身之本**。
> 产物导入表已含 `user32.dll`，**用 W 版不新增任何 DLL 依赖**。

```go
// MessageBox 弹一个模态消息框。PE 里唯一可靠的可读输出通道：
// 日志文件可能写不了，stderr 被 -H windowsgui 丢弃，控制台不存在。
// **必须用 W 版** —— A 版按 ANSI 代码页（本机 ACP=936/GBK）解释字节，
// Go 的 UTF-8 字符串会乱码。
func MessageBox(hwnd uintptr, text, caption string, flags uint) error {
    lt, err := Ptr(text)      // win.Ptr 已是 UTF-16 且走 wstrKeep 持引用（M1 契约现成）
    if err != nil { return fmt.Errorf("MessageBox: text: %w", err) }
    lc, err := Ptr(caption)
    if err != nil { return fmt.Errorf("MessageBox: caption: %w", err) }
    r, _, e := pMessageBoxW.Call(hwnd, uintptr(unsafe.Pointer(lt)),
        uintptr(unsafe.Pointer(lc)), uintptr(flags))
    if r == 0 { return fmt.Errorf("MessageBox: %v", e) }
    return nil
}
```

> ⚠️ `NewLazyProc` 在 DLL 缺失时是 **panic 不是 error**。包装里要 `recover` 成
> error，否则 panic 会穿透 `boot` 的 defer 直接崩成 exit code 2 —— 恰好是本节
> 要消灭的行为。

**T1-2 · 错误出口统一收口 `fatalExit`**

```go
func fatalExit(code int, format string, args ...any) int {
    _ = logx.Error("!! "+format, args...)        // 日志永远先写
    if !noGUIMode {                              // ⚠️ 见下方 MAJOR
        msg := buildFatalMessage(code, format, args, logPath)
        if err := win.MessageBox(0, msg, "smith - 启动失败", mbFlags); err != nil {
            fmt.Fprintf(os.Stderr, "FATAL: %s\n", msg)
        }
    }
    return code
}
```

> ⚠️ **v1 说"6 处 `return 1` 全部改走它"是对的；但漏了两件事**：
> 1. **无头模式不能弹窗**。`MessageBox` 是**模态阻塞**调用，而 smoke 测试跑的是
>    `smith.exe --no-gui`。一旦走到 `return 1` → 无人点 OK → **进程永挂** →
>    smoke 15s 超时失败。当前**侥幸**没触发（实测走的是 `llm==nil` 的 `continue`），
>    但这是 1 行改动就会踩到的雷。**必须加 `if !noGUIMode` 守卫。**
> 2. **只收 `return 1`，不要收 `return 0`**。`main.go` 里那两处 `return 0` 是
>    **用户主动取消 key 对话框**（属正常退出），给它们弹「启动失败」是错误 UX。

**T1-3 · 修 `return 3` 不可达 + worker 无 recover**

> ⚠️ **v1 的改法在 GUI 模式下不成立**。v1 写"用 done channel 传给 boot"——
> 但 `boot` 此刻阻塞在 `win.Run()` 的消息循环里，**根本不在 select 中**，
> 没人读那个 channel。worker 崩了 `boot` 不会返回。

正确改法三步（缺一不可）：

1. `runWorker` 外包 `defer recover()`：panic 时 `logx.Error` + MessageBox
2. **唤醒消息循环**：`win.PostQuitMessage()` —— 这是让 `win.Run()` 返回的唯一途径
3. **用原子变量传退出码**（**不能用 channel**，理由同上）：
   `atomic.StoreInt32(&workerPanicked, 1)`；`boot` 在 `win.Run()` 返回后检查 → `return 3`

**T1-4 · `--console`：删掉，别留假开关**

理由：PE 里双击 exe **没有父进程控制台**，`AttachConsole(ATTACH_PARENT_PROCESS)`
必然失败；`AllocConsole` 能弹控制台但对 GUI 程序是倒退。**MessageBoxW 才是 PE
场景的正确选择。**

> ⚠️ 若你的实际用法是**在 PE 的 `cmd.exe` 里启动**（`X:\smith.exe`），
> `AttachConsole` 会成功，`--console` 就有价值。**这一点待你确认**（见 §七）。
> 未确认前的零风险做法：保留 flag 但把 usage 改成 `"[deprecated] no-op"`，
> 并在 `boot` 里 `logx.Warn` 一次。

**T1-5 · `tryOpenLog` 不留目录残骸**：`MkdirAll` 与 `OpenFile` 解耦。

### 测试

- `MessageBox` **不能在无头 CI 测**（模态阻塞）。只测纯函数

- `TestFatalExit_NoPopupInNoGUIMode`：断言无头模式下不调 MessageBox

## 三、T2 · Job 杀整棵进程树接入

> ⚠️ **代码已完成，真机项未做** —— commit `40cfa2e`。实施记录见 §十。
> **「真机 PE 验证」这一项至今没有任何实测数据**（见 §八 与 §七 Q3）。

> 风险最高的一批。**本计划已按审阅把"手搓 3 个 Win32 结构体"换成 Go stdlib**，
> 使 §S1 的 386 对齐铁律在本批**根本不触发** —— 这是把风险降一个数量级的关键。

### 现状

`win/job.go` + `win/proc.go` 里 M2 双层防护写得很完整，但**生产零调用点**：

```
grep 全仓：KillTreeSelfContained / CreateJobObject / SetKillOnJobClose /
           AssignProcessToJobObject → 命中只在 job.go、proc.go 各自的 _test.go
```

实际 spawn 是 `tools/exec.go` 的 `os/exec.CommandContext(cctx, "cmd", "/c", args)`：
只能杀 `cmd.exe` 这一个直接子进程。`diskpart`/`dism`/`ping` 等孙进程全部存活，
继续持裸盘句柄。`win/job.go` 注释原话："PE 里会变成僵死的 diskpart / dism 还锁着磁盘"。

### 为什么不能直接用 `os/exec`

已核实（读 Go 1.20.14 `syscall/exec_windows.go`）：`SysProcAttr` 共 9 个字段
（`HideWindow` / `CmdLine` / `CreationFlags` / `Token` / `ProcessAttributes` /
`ThreadAttributes` / `NoInheritHandles` / `AdditionalInheritedHandles` /
`ParentProcess`），**无任何 job 能力**。必须自己调 `CreateProcess`。

### ✅ 改法：直接用 `syscall` 包的结构体与 CreateProcess

> ⚠️ **v1 写"手写 STARTUPINFOW（68 字节）+ PROCESS_INFORMATION + SECURITY_ATTRIBUTES"
> 是本计划最费事又最危险的路线。** Go 1.20.14 的 `syscall` 包**已内置**这三个，
> 布局在所有 Go Windows 程序上验证过（审阅 agent 双架构实测确认）。
> 这些 API 自 Go 1.0 存在，不违反 Go 1.20.14 铁律，也不引第三方依赖。

```go
// 直接用：
//   syscall.StartupInfo        （386=68 / amd64=104，探针实测）
//   syscall.ProcessInformation （386=16 / amd64=24）
//   syscall.SecurityAttributes （386=12 / amd64=24）
//   syscall.CreateProcess(...)
// 只在 si 上填 StdOutput / StdErr / Flags = STARTF_USESTDHANDLES
```

**收益**：§S1 那条"含 64 位成员的手写结构体"铁律在本批**根本不触发**，
不需要新增结构体尺寸门禁。**这是本次审阅最有价值的一条建议。**

### 管道：⚠️ v1 写反了，照做会让 `exec` 失去输出能力

> **v1 写"`SetHandleInformation` 把写端设为不可继承"—— 两个错误叠加**：
>
> **① 前提错**：`CreatePipe` 的两个句柄在 `sa=NULL` 时**默认就不是可继承的**
> （MSDN 原文：*"If NULL, the handle cannot be inherited"*）。
>
> **② 方向错**：写端（stdout/stderr）是**子进程要用的那个**，必须可继承。
> 把它设成不可继承，子进程拿到的是空 stdout/stderr。
>
> **正确写法（照抄 Go 自己的实现**，`syscall/syscall_windows.go`）**：
>
> ```go
> sa := syscall.SecurityAttributes{
>     Length:        uint32(unsafe.Sizeof(sa)),
>     InheritHandle: 1,
> }
> CreatePipe(&rd, &wr, &sa, 0)      // 两端默认可继承
> // 可选：把父进程自己那份读端设为不可继承，避免子进程也持有读端
> SetHandleInformation(rd, HANDLE_FLAG_INHERIT, 0)
> ```
>
> ⚠️ **而且 `CreateProcess` 的 `bInheritHandles` 必须传 `TRUE`** ——
> v1 通篇没提，不传则上面全白做。
>
> ⚠️ `bInheritHandles=TRUE` 会继承父进程**所有**可继承句柄。Go 的解法是
> `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 白名单，但**该特性 Win7 不可用**（见下），
> PE 里不能依赖。**务实做法**：给 `win` 包所有对外句柄加
> `SetHandleInformation(..., 0)`，只留管道写端可继承。

### 排空：⚠️ v1 漏了，会在项目已知故障上死锁

> **v1 伪代码没有排空 goroutine。** 匿名管道缓冲约 64KB，一旦写满，子进程
> `WriteFile` 阻塞 → 永不退出 → `WaitForSingleObject(hProc, INFINITE)` 永远等不到
> → **整个 exec 工具挂死，连 60s 超时都救不了**。
>
> 而 `tools/exec.go` 的注释里**明确记录了这个真实故障**：
> `for /L %i in (1,1,3000000) do @echo ...` 峰值 14.7MB + 43MB heap。
> 14.7MB 远超任何管道缓冲 —— **这个场景必中**。
> `os/exec` 没这问题是因为它内部为每个 pipe 起了 copy goroutine。

**必须有**：

```go
go drain(stdoutRd, cw)   // 循环 ReadFile 到 EOF/err，写入 capWriter（S3 已就绪）
go drain(stderrRd, cw)
exitCode, err := jc.Wait()   // Wait 必须等两个 drain 结束（WaitGroup），否则丢尾部输出
```

### 句柄：⚠️ v1 算错了，且忽略 KILL_ON_JOB_CLOSE 耦合

**7 个句柄，不是 6 个**（3 + 4）。关闭时机必须写死：

| 句柄 | 何时关 |
|---|---|
| `hThread` | `ResumeThread` 成功后**立即**关，不等 `Close()` |
| `hProc` | `Wait()` 里 `GetExitCodeProcess` 之后关 |
| 管道 4 个 | 两个 drain goroutine 结束后关 |
| `hJob` | **只在启动失败路径 / `Kill()` 之后关** |

> ⚠️ **`job.go` 已设 `KILL_ON_JOB_CLOSE`（`jobObjectLimitKillOnJobClose`）**，
> 所以 `CloseHandle(hJob)` **会杀掉整棵树**。任何"启动中途失败/提前返回"的
> 路径上，`defer Close()` 会连带杀掉一个还在正常运行的子进程树。
> `Close()` **必须无条件关 hJob 是不安全的** —— 要么按上表分时机关，
> 要么把 `killOnJobClose` 设为 false、改在 `Kill()` 里显式 `TerminateJobObject`
> （语义更直观）。**两种都行，但必须选定一个并写进注释。**

### 两级失败点要拆清（v1 混写了）

```
L1  CreateProcess(BREAKAWAY) 失败  → 重试 CreateProcess(不带该 flag)
L2  AssignProcessToJobObject 失败   → 走 T2-4 的 KillTree 降级链
```

`CREATE_BREAKAWAY_FROM_JOB` 是 `CreateProcess` 的 `dwCreationFlags`，
**不是 `AssignProcessToJobObject` 的参数** —— v1 把两个失败点混在一起，
会写错重试逻辑。两级各自的**日志标记必须不同**（PE 现场无法复现，
日志是唯一线索）。

> ⚠️ **绝对不要用 `PROC_THREAD_ATTRIBUTE_JOB_LIST`**：SDK `winbase.h` 用
> `#if (_WIN32_WINNT >= _WIN32_WINNT_WINTHRESHOLD)` 门禁，而
> `_WIN32_WINNT_WINTHRESHOLD = 0x0A00` = **Windows 10**。头文件层面排除 Win7。

### 降级链（T2-4）

`AssignProcessToJobObject` 失败（Win7 已在父 job 里且不允许 breakaway）时，
**不能变成"没有中止机制"**：

```
TerminateJobObject 成功            → 整棵树已死
       ↓ 失败
KillTreeSelfContained(pid, name)  ← M2 双层防护（照抄 spike，不要重写）
       ↓ 失败
OpenProcess + TerminateProcess    ← 只杀直接子进程，至少不比现在差
```

**日志里必须明确记录走了哪条**。

### `proc.go` 两处顺带修

- `KillTreeSelfContained` 签名改 `(int, error)`（L1：现在返 `(int, []string)`，
  调用方只能遍历 slice 猜成败）
- 轮次之间补 `sleep(300)`（`spike/job` 有、产品代码没有）。**后果**：
  `TerminateProcess` 后内核未回收 PID，下一轮快照看到同一批"正在终止"的进程
  → 重复 kill → 三轮预算被同一批吃光，**多轮设计的初衷被架空**

> **实锤**：SDK `um/sysinfoapi.h` 里

>     DWORD dwLength;        DWORD dwMemoryLoad;
>     DWORDLONG ullTotalPhys;  ...  DWORDLONG ullAvailExtendedVirtual;
> } MEMORYSTATUSEX;
> ```
> 成员是 **`DWORDLONG`（unsigned __int64）不是 `SIZE_T`**。

>

>
> | | cbLength | 结果 |
> |---|---|---|
> | 386 现状（uint64）| 64 | ✅ `ret=1` TotalPhys=68.6GB |
> | 386 v1 处方（uintptr）| 36 | ❌ `ERROR_INVALID_PARAMETER` |
>

> 处方却写"改成 36"。**那份数据恰好证明 36 是错的。**
>
> **结论：现状是对的，不改。** v1 §九③"隐藏前置依赖"整段作废 ——
> **T3 没有隐藏前置，可以与 T1/T2 解耦并行。**

**若确有局域网中转，正确解法不是放宽检查**，而是：给中转挂自签证书 →

bundle 且 `systemPool=false`（走纯 Go 校验、不碰系统根库），**客户端零改动**
（复审已核实 `llm_hardening_test.go` 里有"绝不能用 SystemCertPool"的断言）。

> ⚠️ **但自签 CA 有爆炸半径，方案里必须写明**（复审补充）：把自签 CA 并进
> 公共 bundle 后，**这把私钥的签发能力对全项目所有 https 连接生效** ——
> 不只是那个中转。若中转机器后来被拿下，攻击者可以签任意域名的证书，
> 而项目所有 https 出站都会信任它。
> 正确做法：**私钥离线保管**，或用**独立 CA 文件 + 独立 build tag** 供
> 内部中转场景使用，而不是并进公共 bundle。

## 九、这个计划自己的风险

**① T2 是唯一可能"改坏比不改更糟"的批次。** 它动 Win32 互操作 + 管道 + 多线程。
本计划已按审阅把它从"手搓 3 个结构体"改成 **stdlib**，去掉了最大的一块对齐
风险；但**管道排空、`bInheritHandles`、`hJob` 与 `KILL_ON_JOB_CLOSE` 的耦合
这三处仍然要一次做对**。建议：单独 commit、单独复审、真机各验一次。

**② T3 已解除与 T2 的耦合**（v1 的 T3-2 是伪依赖），可与 T1 并行。

**③ 计划本身也曾出错，教训写在这里：** 本计划的 v1 有 3 个 BLOCKER 级技术事实
错误 —— 管道继承方向说反、结构体"已在门禁内"是虚假安全感、以及 **T3-2 会把
`MemoryStatus()` 从可用改成必然失败**（还附带了恰好否定自己的实测数据）。
**审计报告和计划本身都会错。** 所以每条"改法"都只是**方向**，
真正的实现要在探针实测上落地 —— 上一轮 worker S5 实测推翻了"argv 直传"的
指令，就是最好的例子。

**④ 落地时又暴露出一条计划没写的前置：`kill` 工具的签名改造被排在了 T2 的
「`proc.go` 两处顺带修」里，而 T3 落地在 T2 之前。** 结果 T3 只能把 `kill`
注册成"未接入"。**不是忘了做，是依赖顺序和计划里的批次顺序冲突。**
教训：跨批次的依赖要么显式写进「批次总览」图，要么在下一批的动手前重新对一遍代码。
