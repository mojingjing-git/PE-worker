# GUI 设计与命名建议

> 前提：Win7 PE / XP PE 优先，兼容 Win10 / 11 PE；有网；有 ToDesk；agent 只做读 / 写 / 执行命令。
> 结论：GUI 要做，而且**必须做** —— 因为「LLM 干了什么」这件事，在 PE 里靠黑框命令行根本看不清。
> 但只能做**一种形态**：原生 Win32 控件，单窗口三区布局。

---

## 1. 命名建议

### ⚠️ `tinker` 撤回：撞名比预想的严重

后来查清楚了，`tinker` 的撞名情况不乐观：

| 撞谁 | 严重程度 |
|---|---|
| **Tinker（Thinking Machines 的 LLM 训练 API）** —— `tinker-docs.thinkingmachines.ai` | 🔴 **最致命：同领域（LLM）重名** |
| **腾讯 Tinker**（微信开源的 Android 热修复框架，约 17k★） | 🟠 中文技术圈认知度极高，会被误解 |
| Laravel `artisan tinker` | 🟡 领域不同，影响小 |
| Tinkers' Construct（Minecraft 模组） | 🟡 无关 |
| 读音近乎 **Tkinter**（Python 的 GUI 库） | 🟠 容易被听成 / 记成 GUI 库 —— 这也是"tinker 不是 GUI 的名字吗"这个疑问的来源 |

**结论：不推荐 `tinker`。**

### 备选方案（按推荐度）

既然现在**加了视觉支持**，"眼睛"成了核心能力，"手和眼"的隐喻就值得放进名字里。

| 名字 | 意象 | 优点 | 风险 |
|---|---|---|---|
| **`owl`** ⭐首推 | 猫头鹰 | **3 字母，PE 里手敲最省事**；眼 = 视觉支持；夜 = 系统瞎掉的时候它看得见；好念好记，中文可叫「夜枭」 | OWL 是 W3C 本体语言的缩写，但那是标准不是软件，实际不冲突 |
| **`smith`** | 铁匠 | **语义最贴"修机器"**；直接对上原本想用的中文昵称「小铁匠」；5 字母；无知名软件撞名 | 意象偏"打铁"，不含"看" |
| `wrench` | 扳手 | 工具感最直白，一看就知道是干活的 | 略硬，不像 agent，更像工具库 |
| `talon` | 猛禽的爪 | 爪 = 手、猛禽视力 = 眼，手眼俱全；独特不易撞名 | 略生僻，第一次看到要想一下 |
| `mote` / `wisp` | 微尘 / 一缕轻烟 | 极简意象好 | 语义不直观，不看解释猜不出是干嘛的 |
| `peagent` | PE + agent | 一眼看懂 | 平淡，无记忆点 |

**我的建议：`owl`**（首推，因为视觉是它现在最有辨识度的能力）**或 `smith`**（更保险、更贴"修机器"）。

**建议的命名方案（以 `owl` 为例）：**

```
可执行文件   owl.exe             ← PE 里手敲，全小写、≤8 字符
配置文件     owl.ini
窗口标题     owl — PE agent
日志前缀     ai >  /  you >  /  ->  /  <-  /  !!
中文昵称     夜枭
```

命名要一次定死这五处，别后面改（PE 里改文件名很烦）。

## 2. WinPE 里能不能做 GUI？——能，但只有一条稳妥路线

WinPE 有完整的 `win32k.sys` + `user32` + 桌面（`Winsta0\Default`），所以**创建窗口是可以的**，PE 里那些 GUI 工具箱就是证明。但选型几乎没有余地：

| 方案 | 可行性 | 原因 |
|---|---|---|
| **user32 自带控件**（EDIT / LISTBOX / STATIC / BUTTON） | ✅ **唯一稳妥选择** | 这些是 user32 内建类，任何 PE 都有 |
| comctl32 控件（ListView / TreeView / ProgressBar） | ⚠️ 有风险 | 精简 PE 可能裁掉 `comctl32.dll`；视觉样式还要额外挂 manifest |
| HTA / `mshta.exe` | ❌ | 需要 `WinPE-HTA` 可选组件；PE 里的 IE 内核也是残的 |
| 自绘 GDI 界面 | ⚠️ | 能做，但工作量大几倍，且失去 EDIT 控件自带的选中/复制/滚动 |
| Qt / Slint / 任何 GUI 框架 | ❌ | 依赖体积和运行库都过不了 PE 这一关 |

**关键收获：别小看多行 EDIT 控件。** 它免费送你四件在 PE 里极其重要的能力：
1. 垂直滚动
2. 鼠标选中
3. **Ctrl+C 复制**（排查问题时把日志贴出来全靠它）
4. 自动换行

用 comctl32 的 RichEdit 或自绘文本区，这四样都得自己实现。

## 3. 界面设计：单窗口三区布局

不要做多窗口、不要做标签页、不要做侧边栏。**一个窗口，从上到下三块。**

```
┌──────────────────────────────────────────────────────────┐
│  tinker - PE agent                                    _ □ X│
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ┌──────────────────── ① 日志区（只读多行 EDIT）───────┐  │
│  │ you > 帮我看看 C 盘还剩多少空间                      │  │
│  │ ai  > 先查一下磁盘信息。                             │  │
│  │   -> diskinfo                                        │  │
│  │   <- ok  C: 剩余 12.3 GB / 60 GB (NTFS)             │  │
│  │ ai  > C 盘只剩 12.3 GB，建议先清理 X:\Temp。         │  │
│  │   !! 上面这条命令超时了，已中止                       │  │
│  │                                                      │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                          │
│  ┌────────────────────────────② 输入区──────┐ ┌────┐┌────┐│
│  │ 输入指令，Enter 发送                      │ │发送││停止││
│  └──────────────────────────────────────────┘ └────┘└────┘│
│                                                            │
│  ③ idle · X:\ · model=gpt-oss:20b · 12.4s                 │
└──────────────────────────────────────────────────────────┘
```

### ① 日志区 —— 用前缀区分角色，不要用颜色

只读多行 EDIT，用**前缀 + 对齐**区分消息类型：

| 前缀 | 含义 |
|---|---|
| `you > ` | 用户输入 |
| `ai  > ` | LLM 的文字回复 |
| `  -> ` | 发起工具调用（带工具名和参数摘要） |
| `  <- ` | 工具返回结果 |
| `  !! ` | 错误 / 超时 / 被中止 |

> 为什么不用颜色？多行 EDIT 要上色只能用 RichEdit（comctl32，见第 2 节的风险）。前缀方案零成本、可复制、纯文本还能直接存档。**先做前缀，颜色留给后面的第二版。**

### ② 输入区 —— 输入框 + 发送 + 停止

- 单行 EDIT，Enter 发送
- **`停止` 按钮是必需品，不是可选项** —— PE 里跑个卡住的 `chkdsk` 很正常，没有中途取消就只能杀进程
- 按钮文字直接写 `停止 (Esc)`，让用户知道快捷键

### ③ 状态栏 —— 一行，但信息密度要高

`idle · X:\ · model=gpt-oss:20b · 12.4s`

四个字段各有用处：
- 当前状态：`idle` / `thinking...` / `running: exec` / `cancelling...`
- 当前工作目录（省得用户猜相对路径的基准）
- 当前模型（排查"怎么答得不一样"）
- 上一次调用的耗时（判断是不是网络慢）

## 4. 易用性的 8 个关键细节

前 3 条是**必须做**，不做就是"能不能用"的问题；后 5 条是"好不好用"。

### ① 界面绝对不能假死 —— 这是最容易踩的坑

Win32 窗口如果消息循环被阻塞超过几秒，Windows 会直接给它画上"未响应"的白屏。而 agent 的每一步（HTTP 请求、`exec` 一条耗时命令）都是阻塞操作。

**必须的线程模型：**

```
主线程（UI）           工作线程
─────────────         ─────────────
消息循环              agent loop
  ↑                     ├─ HTTP 请求（慢）
  │ PostMessage         ├─ 执行工具（慢）
  └── 日志行字符串 ──────┘
     （UI 线程负责 free）
```

三条硬规矩：
1. **工作线程永不直接碰控件**，只 `PostMessage` 把日志行丢给 UI 线程
2. **字符串所有权跟着消息走**：工作线程 `HeapAlloc`，UI 线程收到后负责 `HeapFree`
3. **绝不用 `SendMessage` 从工作线程发消息** —— `SendMessage` 是同步的，UI 线程一旦在忙就死锁

> 这套模型我已经写进 `src/tinker.c` 了，直接看 `WorkerProc` 和 `WM_APP_LOG` 两处就能明白。

### ② Esc = 随时中止

在消息循环里拦 `VK_ESCAPE`，置一个 `g_cancel` 标志。工作线程在每个等待循环里检查这个标志，一旦置位就 `TerminateJobObject` 杀掉整棵进程树。

**为什么用 Job Object 而不是 `TerminateProcess`？** 因为 `TerminateProcess` 只能杀直接子进程。`cmd /c diskpart` 这种会派生孙进程，只杀 `cmd.exe` 会留下一个孤儿 `diskpart` 继续锁着磁盘。Job Object 设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 能整棵杀干净 —— 这个坑我在 PE 里见过太多次了。

### ③ 日志区要有上限

多行 EDIT 不是无底洞。日志涨到几万字符后，每次追加都会变慢甚至卡顿。做法：**超过阈值就把前半截删掉**（`EM_SETSEL` 选中前一半 + `EM_REPLACESEL` 替换成 `...`）。骨架里阈值设的 60000 字符。

### ④ Enter 发送要自己拦

普通 EDIT 控件放在**非对话框**窗口里时，按 Enter 只会"叮"一声告警 —— 因为没有默认按钮接管。所以在消息循环里判断 `msg.message == WM_KEYDOWN && msg.wParam == VK_RETURN && GetFocus() == g_input` 然后手动调发送。

### ⑤ 窗口尺寸要自适应

PE 经常是 800×600 或者更小的分辨率。窗口创建前用 `GetSystemMetrics` 查屏幕，**超出就缩到屏幕内**，然后居中。别硬编码 1024×768。

### ⑥ 启动就把自检结果打出来

第一行日志就写 `tinker skeleton up - exec path wired, agent loop pending`，加上 `sysinfo` 的关键字段。这样用户一打开就知道"它活着、它认得出这个 PE"。

### ⑦ 发送按钮在忙碌时变灰

比弹错误提示友好。至少要像骨架里那样在日志里提示 `busy - press Esc or Stop first`，而不是静默吞掉。

### ⑧ 中文显示：字体让系统自己挑

用 `GetStockObject(DEFAULT_GUI_FONT)` 取系统字体，然后**只改字号和字符集**（`lfCharSet = DEFAULT_CHARSET`），别硬编码 `"微软雅黑"` —— Win7 PE 根本没有雅黑。`DEFAULT_CHARSET` 会让系统挑它自己有的中文字体。

字号用**固定 -12px（约 9 磅）**，别做 DPI 换算 —— PE 里的 DPI 信息基本不可信，换算出错反而更糟。

## 5. 一个必须知道的编码陷阱

**这是中文项目在 XP/v7 PE 上最容易翻车的地方：**

> 源文件存成 **UTF-8 无 BOM**，里面写中文字符串字面量，在 **VS2015 之前**的 `cl.exe` 里会按**本地 ANSI 代码页**解释这些字节 → 编译出来是乱码。

三种解法：

| 解法 | 说明 |
|---|---|
| **文案放 INI，运行时读**（推荐） | INI 存 UTF-8，读进来用 `MultiByteToWideChar(CP_UTF8, ...)` 转宽字符。零编译期风险，还顺带支持多语言 |
| 源码存 UTF-8 **带 BOM** | MSVC 2010+ 会正确识别，宽字符串字面量 `L"中文"` 能正常编译 |
| VS2015+ 加 `/utf-8` 编译开关 | 最省事，但锁死了工具链版本（而 VS2013 恰好是 XP 支持的黄金版本，见下） |

所以 `src/tinker.c` 我**刻意只写了英文注释和英文 UI 文案**，并在里面留了 `Utf8ToWide()` 工具函数 —— 中文文案按方案一从 INI 加载。

### 顺带一个好消息

**VS2013 (`v120_xp` 工具集) 是最后一个原生支持编译 XP 目标的 MSVC。** 也就是说：想同时覆盖 XP PE 和 Win10/11 PE，VS2013 + `/NODEFAULTLIB` 是一条成熟且被验证过的路。VS2015 之后的 XP 支持都要靠额外装 "C++ Windows XP Support" 组件。

（我在这台机器上没找到可用的 C 编译器 —— 只有 VS2013 的残留组件和 Windows Kits 8.1 的头文件，所以骨架**没法在这里编译验证**，需要你在装了 MSVC 的环境里编一次。）

## 6. 骨架代码说明

`src/tinker.c` 是一个**能编译、能跑**的最小实现，不是伪代码。编译：

```bat
cl /nologo /O1 /GS- /W3 tinker.c ^
   /link /SUBSYSTEM:WINDOWS /ENTRY:WinMainCRTStartup /NODEFAULTLIB ^
   kernel32.lib user32.lib gdi32.lib
```

它已经实现的（都是难的部分）：

| 部分 | 说明 |
|---|---|
| 免 CRT | `/NODEFAULTLIB` + `WinMainCRTStartup`，用 `wsprintfW`（user32 导出）代替 `sprintf`，`HeapAlloc` 代替 `malloc` |
| 只用 user32 内建控件 | EDIT / BUTTON / STATIC，零 comctl32 依赖 |
| 线程模型 | UI 线程 + 工作线程 + `PostMessage` 传日志行 + 所有权转移 |
| `exec` 完整实现 | 匿名管道捕获 stdout+stderr、**不阻塞的读法**、超时、Job Object 杀进程树、NUL 重定向 stdin |
| Esc / 停止按钮 | `g_cancel` 标志 + 全链路检查 |
| 日志裁剪 | 超过 60000 字符自动砍前半截 |
| 屏幕自适应 | 小屏自动缩窗口并居中 |
| Enter 发送 | 消息循环里拦 `VK_RETURN` |

它**没有**实现的（占位在 `WorkerProc` 里）：

```
   1. 把对话序列化成 JSON
   2. POST 出去（bundle 的 curl.exe，或自己走 ws2_32）
   3. 解析 tool_calls -> 分发 -> LogLine(LV_TOOL, ...)
   4. 结果回填，循环到模型返回纯文本
```

代码里两个特别值钱的细节，注释都标了：
- **管道的 `ReadFile` 不能要超过 `PeekNamedPipe` 报的可用字节数**，否则会一直阻塞到管道关闭（经典坑）
- **`GetTickCount64` 是 Vista+ 才有**，XP 上必须用 `GetTickCount` 自己处理回绕

## 7. 渐进增强路线

| 版本 | 内容 |
|---|---|
| **V1（当前骨架）** | 单窗口、日志区、输入区、状态栏、exec、Esc 中止。截图只**打印落盘路径**，人自己在 ToDesk 里打开看 |
| **V2** | 日志上色（加 RichEdit，注意要挂 manifest）、工具调用折叠、状态栏加 token 用量、发送按钮忙碌时变灰、**截图预览窗口**（`WS_POPUP` + `SS_BITMAP` STATIC，PNG 要先解码成 BMP） |
| **V3** | 右侧工具面板（ListBox 列出历史工具调用，点击跳转）、日志导出到文件（`Ctrl+S`） |
| **V4** | 多会话标签页、INI 里的主题/字体配置界面 |

> **为什么 V1 不做截图预览？** 把图显示到 GUI 里要么加一个窗口、要么自绘文本控件（跟"不用 comctl32"的决策直接冲突）。而 PE 场景下**人本来就在 ToDesk 里看着这个桌面**，截图落盘后直接打开就行 —— 先把工具链跑通，别提前做 UI。

**建议 V2 也别急着做。** V1 先在真实 PE 里跑通一次，你会发现真正缺的东西跟现在猜的不一样。
